# Design responsibility without a procedural framework

## Consumer adoption

Use the `Retained design and delegated work` section of `templates/AGENTS.md` in the target
project and install `core` plus `quality`. This is deliberate opt-in specialist exposure;
core remains seven Skills, and the contract still applies without automatic Skill selection.
The supervisor's name/model is not proof of code health. A single agent inherits the same
responsibilities; no mandatory manager/reviewer/worker roster or duplicated review ceremony.

Use preflight to establish real consumers, permitted internal replacement, external/data
obligations, required acceptance paths and the likely next maintenance operation. Do not
invent compatibility consumers, and do not assume unobservable external callers are absent.
Give workers this information and shared semantic ownership, not merely file exclusions.
The supervisor verifies the integrated candidate and may revise its own architecture.

## What changes from the old Skills

The old general quality Skills remain retired. Their `working-contract` destination now
contains explicit design obligations; the optional `code-health` Skill provides the richer
comment/economy/ownership review when needed. This is not a legacy alias or unconditional
Skill chain. Existing NFR, authority, RCA and E2E duties remain unchanged.

A finding needs a location, a current failure or plausible change burden, and a bounded
alternative. No numerical design grade, minimum number of findings, obligatory refactor,
or per-function report. Formatting and project-specific dependency violations belong in
existing mechanical checks; semantic duplication and needless compatibility require context.

## Evaluation

`evals/evolution` retains the actual generated repository across changing requirements.
Run the old instructions, current contract, and contract plus specialists under the same
model/team/harness conditions. Then compare a strong single agent and alternative teams,
holding the final maintainer configuration constant across candidate repositories. Use held-out
projects, repeated runs, blind review and uncertainty before asserting superiority.

Current executable fixture checks exercise real local CLI processes and persisted JSON;
they do not prove semantic ownership, taste, general maintainability or model behavior.
Use absolute diagnostic quantities separately for product/tests/generated code, with analyzer
and rule versions. The independent oracle is a correctness gate, not a Slop Score.

This proposal follows the motivation in [Measuring code sloppiness](https://earendil.com/posts/measuring-code-sloppiness/),
not a claim that any named frontier model has solved oversight. Necessary safety boundaries,
real compatibility and valuable comments are negative controls, not cleanup targets.
