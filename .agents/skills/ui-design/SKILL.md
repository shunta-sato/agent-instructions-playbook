# UI design and previews

Work from the requested interaction, audience, platform and existing design system.
Retain semantic hierarchy, accessibility, states and responsive behavior. Do not
force a style-catalog exercise when the project already has an accepted direction.

For visual exploration, `assets/styles/` contains the seven existing tone/manner
patterns, tokens and style-tile previews. For component/screen construction use
`assets/screens/`; for transition-map review use `assets/flows/`. These are optional
starting assets, not mandatory output layouts, scoring forms or production libraries.
Copy only the asset subtree needed and preserve its relative resource relationships.

Present executable alternatives when the request needs comparison, under the same
interaction and quality contract. Distinguish prototype choices from product-ready
implementation. Use `ui-verification` only when its visual/runtime evidence is needed;
there is no forced design-orchestrator chain or approval stop after the first preview.
