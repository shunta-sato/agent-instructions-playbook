# Playbook authoring

Separate project facts, task intent, specialist knowledge, executable checks and
harness configuration. Keep routine development viable without selecting a skill.
Skill descriptions say when they apply; they are not feature advertisements or
inventories of every word that might appear in a task.

Use an entrypoint with enough decision guidance to select only needed references or
tools. Do not move a long mandatory recipe into a required reference and call that
progressive disclosure. Keep irreducible protocol/authority/evidence invariants;
remove general coding lessons, fixed role assignments and obsolete model scaffolding.

Before changing a control, identify the failure or requirement it protects. Preserve
its regression case or replace the mechanism with one that checks the actual outcome.
No blanket size quota for product code or a universal retry count. Evaluation should
compare the current playbook, a minimal contract and minimal-plus-specialists on the
same task/environment/model conditions. Schema checks and simulated adapters are not
live model evaluation; report unrun trials as unrun.

Use the repository's current `README.md`, `docs/astra-redesign.md` and `evals/README.md`
when editing this playbook. Do not install contributor-only policy in consuming
projects. Old names and model-specific routing have no compatibility guarantee.
